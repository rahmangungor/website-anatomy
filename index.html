The journey of a request

The terminal on the left is a visitor's browser and the front rail is the path of an HTTPS request. The domain is first looked up in the DNS card file, then the carrier box is locked and rides into Cloudflare's X-ray tunnel. There the lock is opened, the WAF scans the request, and it is either answered from the cache shelf on the roof or sent on to the VDS on the right. The back rail is a separate deploy line from GitHub to the VDS. Hover or click a station, or pick one below.

      The padlock on the box is TLS encryption. It is locked in the browser and opened at Cloudflare, because the WAF and the cache can only work on decrypted content. Cloudflare then opens a separate encrypted connection to the server, and nginx on the VDS opens the lock again. The shelf on top of the tunnel is Cloudflare's cache: the top row holds copies of this site, the bottom row belongs to other sites on the same edge server, and a deploy purges this site's copies. The open server in the rack is the physical machine that is split into VDSs; the four glowing cores are the ones reserved for you. Timings are representative and vary with location and hardware.

      What this is

      • A simplified, interactive model of how a small website on a VDS is served through Cloudflare and deployed from GitHub.
      • A way to see where DNS, TLS, the WAF, the cache and the deploy pipeline sit in a single request's journey.
      • Plain HTML, SVG and JavaScript in one file: no framework, no build step to view it, no tracking.

      What this isn't

      • A network simulator: no packets are sent and the timings are representative.
      • A reference architecture or a security checklist; real setups vary a lot.
      • Affiliated with Cloudflare or GitHub.
